# The Wrong Substrate: Why Inherited Engineering Wisdom Fails Software

## Abstract

The Wrong Substrate: Why Inherited Engineering Wisdom Fails Software The verification epistemology applied to safety-critical software — reviews before cost cliffs, component qualification, certificate inheritance, traceability-based safety cases — was built for hardware engineering, where it is successful. These methods are calibrated to a substrate with geometry, locality, dissipation, and stable constitutive laws. The transfer to software failed because software is a qualitatively different physical substrate. It provides no native locality structure that makes declared boundaries principled upper bounds on causal influence. Its state spaces are ageometric, causal propagation is unbounded, distinctions accumulate without dissipation, and execution is computationally irreducible. Methods calibrated to the physical substrate make systematically wrong predictions on this one — not through misapplication, but because they are applied to the wrong kind of thing. This paper identifies seven predictable prediction failures: two prior errors (the Platonic object error and the ur-error that software has no objects with stable causal boundaries at runtime) and five downstream errors (locality, transitivity, enumeration, intent-structure, and hidden-variable). Activities misclassified as evidence for properties they cannot establish are diagnosed as scope misattribution — a structural diagnosis, not a condemnation. Real software systems contain volume-law cores by design — computational regions where irreducible coupling is the functionality — surrounded by infrastructure declared as area-law but built from the same ageometric substrate. The paper develops this combustion chamber topology as the governing architectural picture: the computational fire is irreducible by design; the surrounding software steel is contingent by substrate; and whether the steel holds is an empirical question that only execution can answer. The constructive turn names system observation as a first-class engineering discipline that safety-critical practice currently lacks — illustrated by the contrast between SpaceX's flight-instrumented development model and the 2024 Starliner Crewed Flight Test, where the independent NASA investigation identified that insufficient telemetry on prior uncrewed flights allowed anomalies to be accepted and closed without root cause, directly enabling the same systemic issue to threaten crew safety on the crewed flight. Hyperscale operators, systems-theoretic safety analysis (STAMP/STPA), and the spaceflight contrast all converge on the same epistemic posture: execution as ground truth, structural descriptions as hypotheses. The paper closes with three organisational consequences: decoupling accountability from components, engaging regulators for methodology recalibration, and the economic argument that makes realignment inevitable. A template for an honest safety argument, a hierarchy of evidence, and the organisational vocabulary needed to distinguish volume-law cores from syntactic and organisational components provide immediate practical instruments.
